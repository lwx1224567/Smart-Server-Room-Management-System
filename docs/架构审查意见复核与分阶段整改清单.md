# 架构审查意见复核与分阶段整改清单

日期：2026-10-17。依据用户提供的架构审查意见及当前工作区源码。

本轮为定向静态复核：完整读取前端认证、工单、监测 Store、首页协调器及相关客户端；定向核查三个后端核心 Service 的初始化、业务入口、事务及会话实现，以及三维核心入口、方法边界和资源释放。未逐行完成所有业务代码审计，未运行应用、构建、数据库迁移或测试。以下行号以本轮工作区为准。

## 1. 结论与原意见的修正

建议保留“模块化单体、渐进重构”的方向，但暂不整体迁移到 modules/。当前应先修会话生命周期、异步回包归属及控制模式判断，再拆职责。

| 原意见 | 源码复核 | 对整改的影响 |
|---|---|---|
| API 与 Service 不统一 | `api/platform/client.ts` 已全部委托 `consoleApi`，普通 JSON 请求存在共享认证及响应解析；助手 SSE 独立 | 拆清职责即可，不需要再造第二套 JSON 客户端；SSE 保留独立流解析 |
| Pinia 与普通响应式模块并存需要整改 | 并存属实，但工单、监测都已有清理事件和请求代次保护 | 保留已有行为，先补齐缺口，不能简单以“全部改 Pinia”当作修复 |
| 数据库初始化入口不清楚 | `数据库/README.md` 已声明旧导出不可用于当前初始化；migrations README 有阶段说明 | 需要补完整的新库初始化流程及更新过时说明，不能称完全没有文档 |
| 三维核心需要拆分 | 属实，但已有 AbortController、帧取消、观察器断开、材质/纹理/几何体释放及公开操作接口 | 保留资源所有权及现有 API，不得在拆文件时丢失释放逻辑 |
| Agent 会话需要梳理持久化 | 当前会话实际保存在内存，启动时清空旧表及相应备份记录 | 目标应是明确内存会话生命周期，而非默认补建持久化层 |
| P0 级别的状态与分层问题 | 原报告已说明是分析优先级；本轮也未发现仅由目录导致的紧急故障 | 使用“优先修复、后续治理”表达，避免将架构偏好当严重 Bug |

另一个需要修正的判断方式：`ConsoleService.java` 虽约 127 行、`IntegrationService.java` 约 178 行，但大量方法、SQL、分支压在单行里，行数不能用于横向比较复杂度。格式化与业务重构应分开提交。

## 2. 优先处理的行为问题

以下每项均区分源码事实和场景推断。场景未通过本轮运行复现。

### A1. 检查会话时将临时网络异常也转成退出

- 证据：`前端/smart-park-guat-web/src/services/console.ts:62` 的 `checkSession()` 对 `/auth/me` 的所有异常执行 `clearSession()`；`router/index.ts` 据返回值跳转登录。
- 触发：带有效 token 刷新页面，此时请求超时、网络中断、服务端临时 503 或 JSON 解析失败。
- 推断：有效本地会话被清除，用户被当作未登录。
- 改动文件：`services/console.ts`、`router/index.ts`；后续可提取 `api/http.ts` 与 `api/api-error.ts`。
- 最小修复：保留可判别的 HTTP/业务错误；仅明确的认证失效清除会话。网络不可用应进入可重试的检查失败状态，不能把“检查失败”当“已认证”，也不能直接放行页面。
- 验收：401 清除会话并跳转；超时/503 不删除 token、不错误放行，显示重试；登录后的角色守卫保持有效。

### A2. 工单写入回包缺少会话代次保护

- 证据：`services/work-orders.ts:55` 起，清理事件增加 `generation`，`loadOrders()` 有代次检查；`:86` 的 `createOrder()` 及 `:89` 的 `orderAction()` 在 await 后直接 merge。
- 触发：账号 A 发出创建/操作请求，回包前退出，随后收到成功回包。
- 推断：退出时清空的共享列表可能重新写入 A 的工单；若已登录 B，可能污染 B 的前端状态。这不是已证明的后端越权。
- 改动文件：`services/work-orders.ts`；如同步迁移则归属 `stores/work-orders.ts` 与 `api/work-orders.ts`。
- 最小修复：写入发起时捕获会话代次，成功后仅向原会话的状态合并；不能自动重发写请求。失败后触发的 `loadOrders()` 也要核对原会话，避免旧操作干扰新会话。
- 验收：延迟写入回包跨越退出/重登，旧数据不进入新列表；正常会话写入照常更新；失败刷新不隐式重复写入。

### A3. 能力查询失败与明确未配置硬件网关被合并

- 证据：`views/home/composables/useHomeDashboard.ts:44` 默认 `hardwareControls=false`，`:55` 空 catch；`useCabinetControls.ts:76` 为 true 时走网关，否则在 `:83` 走普通控制状态写入。
- 触发：能力接口还没返回，或者查询失败，用户操作机柜控制。
- 推断：未知网关状态被解释为无网关配置，并进入普通状态写入路径。不能据此推断物理设备已执行或发生危险动作。
- 改动文件：`useHomeDashboard.ts`、`useCabinetControls.ts` 及对应控制 UI。
- 最小修复：使用 loading/ready/error 的能力状态，ready 内再表达明确的配置结果；未知或失败时禁用相关操作并提供重试。对于明确未配置网关是否允许平台状态控制，保留现有业务语义并明确标注。
- 验收：加载中/失败不发送控制写请求；明确已配置仅走网关；明确未配置走既定平台状态路径，界面准确表达其含义。

### A4. 台账 Store 未接入退出清理

- 证据：`stores/platform.ts` 有 `clearSelection()`，但没有整体清理方法或 `console-session-cleared` 监听；相比之下，`stores/monitoring.ts:238` 和工单模块都监听该事件。台账 `load()` 仅在下一次加载时清空状态。
- 推断：退出后内存仍保留机房/场景/台账详情，旧在途台账请求也未因退出统一作废。首页重挂载会主动 load，能缓解部分路径，不能据此宣称每次切换用户都出现旧数据。
- 改动文件：`stores/platform.ts`、会话清理协调模块。
- 最小修复：提供整体 clear，同时推进详情和加载代次；清空台账、选择及会话内缓存。保持清理动作幂等。
- 验收：退出后台账状态为空；退出前在途成功回包不能回填；重新登录能正常加载及选择。

### A5. 普通请求丢弃错误上下文

- 证据：`api/contracts.ts` 已定义 `requestId`、`serverTime`、`error.type/fields`；`services/console.ts:47` 只抛出 `Error(msg)`。
- 影响：调用者不能可靠区分 HTTP 状态、字段校验、认证、冲突和临时不可用，也失去服务端请求关联信息。
- 最小修复：结构化 ApiError 保留 status、type、fields、requestId；UI 继续展示友好 msg。泛型默认 any 可逐业务收紧，不需一次修改所有调用点。
- 验收：400、401、409、503 的状态和字段可被调用者读取；非 JSON 错误响应可理解；正常响应解析及来源归一保持兼容。

## 3. 后端核心职责的具体拆分边界

以下为建议目标文件，不是现有文件；第一步可保留原 Service 为兼容门面，逐个转移调用方。避免同一阶段搬包、改 API、改表结构。

| 现有文件 | 确认职责与证据 | 建议目标 | 必须保留的约束 |
|---|---|---|---|
| `service/ConsoleService.java` | `schema():22` 建表/旧账号迁移；密码散列；认证；人员；`createOrder():75`、`action():78`；复检；通知 | `security/AuthService`、`service/person/PersonService`、`service/workorder/WorkOrderService`、`service/notification/NotificationService`；SQL 分别进对应 repository | PBKDF2 与 token 摘要兼容；角色和归属校验；先锁机房再锁工单；expectedState；创建及通知的事务边界 |
| `service/IntegrationService.java` | 规则、采集入库/幂等、告警评估、模型工具及流式输出、视频、硬件命令 | 先抽 `integration/model/ModelGatewayClient`；后续 `CollectorService`、`AlarmRuleService`、`VideoGatewayClient`、`DeviceCommandService` | 入库批次幂等和机房锁；模型流事件；命令 ID 和 actualValue 校验；DEMO 受信入口 |
| `service/AssistantAgentService.java` | `sessions/locks:31` 内存会话；工具执行；确认；SSE 回调；`:37` 旧表初始化清理 | 先抽 `agent/AgentSessionStore`，再抽 `AgentToolDispatcher`、`AgentConfirmationService`；原类保留编排 | 页面/账号/机房隔离；同会话串行；工具白名单和参数校验；确认期限、指纹、requestId；场景动作回执；ThreadLocal finally 清理 |

不能把“Service 内有 SQL”直接等同事务失效。`ConsoleService.createOrder/action` 和 `IntegrationService.collect/ingest` 已有事务声明。抽取服务时需重新核查 Spring 代理调用和传播语义，保留现有集成测试；不能依据同类内部调用就推断外层事务不存在。

### B1. Agent 内存生命周期需要治理

源码事实：会话 key 含账号、机房和页面 ID；`end():58` 删除 sessions 条目，但不移除 locks 条目；本类未见会话 TTL、容量上限或周期回收。

推断：页面 key 长期增加可能使锁映射增长；未成功发送 end 的页面可能留下会话。未做负载测试，不能量化实际内存影响。

建议：先明确单实例的空闲期限和回收规则，再抽 AgentSessionStore。不要直接在解锁后 remove 锁：仍有等待线程时可能让同一 key 出现两把锁，破坏互斥。无需为当前单实例架构默认引入 Redis。

### B2. 网关执行与数据库提交没有原子性

源码事实：`IntegrationService.command():171` 在事务方法内外调网关，再保存命令/读数/控制记录。外部设备不参加数据库事务。

推断：网关执行成功后本地数据库失败，可能出现外部状态已改变、本地记录未提交的情况。未验证网关是否支持按命令 ID 查询或幂等。

建议：先补充命令结果不确定时的查询/对账规则，再决定是否拆短事务。不能简单删掉 @Transactional，也不能把超时后的自动重试作为默认方案。

### B3. 启动迁移与兼容清理应有独立归属

源码事实：ConsoleService 启动建表及迁移旧账号；AssistantAgentService 启动清空旧会话表，并删除备份表中对应条目。后者与“新会话仅存内存”的当前实现一致，但 migrations README 仍描述按账号和机房保存会话的旧阶段。

建议：先更新现状文档，再将初始化/升级移至专门 migration/bootstrap 边界。需要单独明确哪些是一次性升级、哪些是每次启动行为，不能仅搬文件就改变执行时机或删除数据。

## 4. 三维与首页：先约束接口，再拆实现

`useHomeDashboard` 已抽出 `useHomeSceneData` 和 `useCabinetControls`，不能称未拆分。下一步可先独立生命周期轮询和助手连接，保留首页总协调器。业务驾驶舱仍可通过状态切换，无需强制新增六个路由。

`scene.ts` 的 createRoom 当前通过闭包共享 renderer、scene、racks、inspectionClone 等状态。按目录强行拆文件会引入大量上下文参数或全局变量，建议依次抽取：

1. 材质/纹理与基础几何体工厂（原约 143–326 行）：明确缓存及 dispose 所有权。
2. 设备模型工厂（结合 moduleTexture、addInventoryModels）：保持 inventoryId 和拾取层级。
3. 拾取与交互（约 1075 行起）：通过回调访问选择，保留已有事件。
4. 设备抽取/归位（约 1517–1554 行）：保留动画中断、父子层级恢复及巡检关联。
5. 最后才考虑拆 renderer/camera 生命周期；目前 `dispose():1781` 的集中释放必须继续覆盖抽出的资源。

每次保持 createRoom 返回接口兼容。验收包括概览→机柜检视→抽出设备→归位→返回、柜门/锁状态、告警同步、巡检到达/取消、连续挂载卸载。已有释放代码不等同已证明没有 GPU 泄漏，本轮未测。
