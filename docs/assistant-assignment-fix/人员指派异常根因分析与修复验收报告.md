# 小维 Agent 人员指派异常根因分析与修复验收报告

本轮暂停阶段 3C。只读分析后进行了最小范围修复，未连接真实数据库、启动业务服务或执行真实建单/指派。完成后停止等待验收。

## 1. 证据范围与根因

没有找到 WO-2CD26BC2-377 本次真实会话的模型工具参数、Agent trace 或会话快照。只发现前端旧类型检查日志，不能作为本问题证据。因此无法断言三次生产失败的唯一原因，也不能断言真实模型传入的是用户ID、账号、空参数或错误工单。

修复前 AssistantAgentService 存在以下问题：

1. captureSelection 的序号正则要求整段文本完全匹配“第一个”等短句，完整指派句中的“第一个”不会被选中。这是已通过修复前模拟测试证实的缺陷。
2. prepare_assignment 先经过 selected(order)，再验证 selected(person)。captureSelection 仅处理当前 choiceKind；推荐人员后 choiceKind 切为 person，之前多工单列表的 orderSelected 可能未更新，导致用户已明确写出工单编号仍被旧工单选择状态拦截。不是简单的“人数大于1就无条件拒绝”：selected 匹配到已选ID时本会放行。
3. 人员账号/姓名匹配使用 contains；账号存在前缀关系时可能发生冲突。稳定人员ID在原人员分支仅支持整句等于ID或“选择ID”，不能稳定处理完整指派句。
4. 工具 schema 只接受必填 ownerAccountId，缺少账号、姓名、推荐序号的明确参数；模型必须先转换稳定ID。是否本次实际发生参数误传仍缺少真实 trace。
5. 会话保留 personChoices（包含原始人员 id/userName/displayName/skills，按 Service 顺序）、personSelected，以及通用 choiceKind/choices；但人员列表没有绑定当前机房、工单状态指纹或有效期。当前工单 ctx.orderId 仅由部分查询/准备路径更新，recommend_people 原本不建立独立工单绑定。会话本身已按账号+机房+页面ID隔离。
6. recommend_people 原返回技能匹配列表及全部启用列表，模型可展示两组；序号未明确唯一对应哪一组。仅凭用户转述无法判断此次“admin1”是否角色错误：账号名不是角色，ConsoleService.people 实际只查询 MAINTAINER。

已完成只读核查：ConsoleService.people 限制角色为 MAINTAINER；ConsoleService.action 的 assign 分支要求管理员、合法工单状态，并在数据库事务内重新查询启用 MAINTAINER。现有权限与写入状态规则保留，未修改 ConsoleService。

## 2. 模拟工具参数与修复前证据

纯 Mockito 测试手动实例化 Agent，JDBC、模型和业务 Service 均为 mock，不启动 Spring，也不调用 schema。

初始两项测试结果：1 项通过、1 项失败。完整工单指派句“把工单 WO-2CD26BC2-377 指派给第一个去处理”，在有效两人推荐后模拟模型调用：

```json
{"name":"prepare_assignment","arguments":{"orderId":"WO-2CD26BC2-377","ownerAccountId":"5"}}
```

修复前实际工具 trace 返回 `{"status":"CLARIFICATION_REQUIRED"}`，pending 为空。证据保存在 reproduction-before.txt。

另一项 user1 测试在某些上下文中修复前就通过；这反证了“只要两个人就必然失败”的解释。新增测试同时覆盖旧多工单候选未选中、推荐人员后再明确工单的路径。

修复后模拟模型可使用以下任一字段（工单仍必填），均经服务端当前用户选择和实际人员目录校验：

```json
{"orderId":"WO-2CD26BC2-377","ownerUserName":"user1"}
{"orderId":"WO-2CD26BC2-377","ownerDisplayName":"李四"}
{"orderId":"WO-2CD26BC2-377","ownerAccountId":"5"}
{"orderId":"WO-2CD26BC2-377","recommendationIndex":1}
```

这些是测试夹具参数，5 是模拟用户稳定ID，不是已查询到的真实 user1 ID。未将它写入真实数据，也未硬编码进生产逻辑。

## 3. 修改文件与规则

生产文件仅一个：后端/smart-park-guat-server/src/main/java/cn/guat/smartpark/service/AssistantAgentService.java。

- 为 prepare_assignment 增加可选 ownerUserName、ownerDisplayName、recommendationIndex，保留字符串 ownerAccountId；缺少人员时返回可操作的候选而不猜测。
- 人员选择移出通用 captureSelection；在模型已选择 prepare_assignment 后确定性校验。所有用户自然语言仍先进入大模型循环，没有恢复自然语言快捷分流，也没有新增前端规则。
- 账号和稳定ID按完整标记精确匹配，区分 user1 与 user10；没有强标识时按用户给出的姓名核对候选，重名不放行。提供的多个工具选择字段必须与解析对象一致；冲突需澄清。
- 用户必须有本轮人员指向；模型单独提供一个猜测ID不能生成待办。不凭旧 personSelected 静默复用人员。
- 支持完整句中的“第一个”“第二个”等（中文一至十或数字），仅映射当前有效推荐序列；账号与序号指向不同对象、多个序号、越界或参数不符均澄清。
- 推荐快照绑定机房、工单、工单状态指纹、创建时间和当前请求；有效期10分钟。序号不能引用本轮尚未展示的新列表。切换工单工具目标、页面/会话变化、状态指纹变化、过期使旧序号失效。
- 返回 selectionCandidates 和 selectionPolicy，明确序号只对应服务端原序；提示模型不得混合 enabledPeople 或重排。账号/ID可明确选择其他符合既有资格的人员，不要求必须技能第一名。
- 工单以当前机房真实订单为准，用户明确工单不再受旧多工单选择状态阻挡；检测到工具工单与本轮明确的其他工单冲突会拒绝。
- prepare 每次重读既有维保目录，拒绝停用或不符合角色者，检查工单可指派状态；真实确认继续走原 token/有效期/状态指纹/权限/事务校验。

测试文件：
- 新增 AssistantAssignmentTest.java：10 项场景组合。
- 修改 AssistantUnifiedAgentTest.java：既有指派用例明确给出用户账号，不再用“准备操作”加模型猜测ID作为用户选择。

额外新增本报告、基线与测试证据，见本目录。baseline.json、after-sha256.json 记录修改前后哈希，git-status-before.txt 记录原工作区。修改前已有文件哈希与已记录基线一致；未清理任何其他未提交工作。旧 API、前端、Three.js、数据库结构/数据策略、模型提供商及依赖均未变更。

## 6. 真实联调条件与独立方案

已具备进入受控联调评审的代码与模拟证据，尚不能宣称生产问题真实闭环验收。缺少原会话 trace，需在后续获准的既有运行环境收集实际 prepare_assignment 的参数、工具结果及会话工单/候选上下文；不要为收集证据擅自启动服务或连接数据库。

建议下一轮先做“只准备、不确认”的真实模型/浏览器验证：专用测试账号与测试工单，依次验证账号、姓名、首位序号、重名、切单、过期，检查卡片的工单与人员稳定ID；不点击写入按钮。启动方式须单独审查，应用初始化存在兼容表操作，本轮没有启动。

如需真实写入：另行批准专用隔离测试库、测试工单和测试维保账号、允许的一次确认及清理责任；观察 token/requestId、业务状态和负责人，模拟回执丢失仅查询状态、不得自动重提。不得拿 WO-2CD26BC2-377 擅自作真实写入样本。

限制：模型仍可能错误选工具、漏传或误传选择信息；服务端会澄清或拒绝，真实模型是否遵循 selectionCandidates 顺序尚待验证。现有账号目录没有新增人员-机房关系字段，沿用 ConsoleService 的管理员/维保资格体系及工单机房归属规则，不虚构额外资源权限。中文姓名从用户文本核对候选并非开放模糊搜索，不支持别名、近似姓名或猜测。新增序号只覆盖明确“第N个/位”表达，更复杂转述交由模型澄清，不能保证任意中文表达都成功。
